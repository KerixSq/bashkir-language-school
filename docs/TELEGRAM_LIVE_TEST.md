# Настоящий Telegram live smoke test

Это отдельная ручная проверка цепочки **Telegram-клиент → Bot API → единственный long polling → aiogram → PostgreSQL → Bot API → Telegram-клиент**. `tests/bot_integration.py` сохранён: он проверяет FSM с заменённым транспортом и не является live E2E.

## Требования и границы

- Существующий тестовый бот, отдельные тестовые аккаунты и отдельная база с текущими SQL-файлами и настоящим корпусом БГПУ. Не используйте рабочие школьные результаты.
- Один экземпляр polling. Остановите экземпляры того же токена на других компьютерах, серверах и в Compose. Bot API не даёт надёжного read-only способа обнаружить все чужие polling-процессы.
- Python и обычные зависимости проекта: `python -m pip install -r requirements-dev.txt`. Новых сетевых библиотек и SQL-миграций нет.
- Telegram-клиент у человека. Бот не может отправить себе сообщение от обычного пользователя через Bot API.

Live smoke **не вызывает getUpdates**, не отправляет сообщений, не меняет webhook, не удаляет очередь и не пишет в БД. Он вызывает настоящие `getMe` и `getWebhookInfo`, читает состояние только выбранного тестового аккаунта и наблюдает диагностические квитанции работающего бота. Внешние пользователи в тестовом режиме игнорируются без ответа.

## Приватный env

Создайте `.env.live` (исключён из Git). Значения токенов и кодов не вставляйте в чат, скриншот или отчёт:

```dotenv
LIVE_TELEGRAM_TEST_ONLY=1
LIVE_TELEGRAM_TEST_USER_ID=ЧИСЛОВОЙ_ID_ТЕСТОВОГО_АККАУНТА
TELEGRAM_BOT_TOKEN=ТОКЕН_СУЩЕСТВУЮЩЕГО_ТЕСТОВОГО_БОТА
SUPABASE_URL=http://127.0.0.1:54321
SUPABASE_SECRET_KEY=СЕРВЕРНЫЙ_КЛЮЧ_ТОЛЬКО_ТЕСТОВОЙ_БАЗЫ
```

`LIVE_TELEGRAM_TEST_ONLY=1` — явное подтверждение, что указанная база выделена под QA. Скрипт не может определить из одного URL, является ли база рабочей. Env выбирается явно, без подмешивания облачных ключей из родительского процесса. Для env формата Compose допускаются `SERVICE_ROLE_KEY` и стандартный loopback-адрес; для нестандартного порта укажите `SUPABASE_URL` и `SUPABASE_SECRET_KEY` явно.

Необязательные поля: `LIVE_TELEGRAM_PROBE_FILE` (абсолютный путь, по умолчанию `.live-telegram/probe.json`), `LIVE_TELEGRAM_JOIN_CODE` (короткий код приглашения **тестового** класса ученика). Код преподавателя вводится человеком непосредственно в Telegram; диагностический журнал его не сохраняет.

Если проект запускается через Compose, используйте отдельный проект/том и свободный порт по действующим инструкциям. Не запускайте `down -v`, reset или SQL чистой установки поверх рабочей базы. Уже работающая отдельная PostgreSQL/PostgREST среда тоже подходит: Bot API не требует Supabase Auth для Telegram-профиля.

## Два окна PowerShell на Windows 11

Из корня проекта, после остановки других экземпляров этого токена:

```powershell
# Окно 1: существующий бот, один polling-процесс, диагностика только тестового ID.
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_live_telegram_test.ps1 -EnvFile .env.live -BotOnly

# Окно 2: управляемый live smoke. Сначала Enter в консоли, затем действие в Telegram.
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_live_telegram_test.ps1 -EnvFile .env.live
```

Если окружение Python находится не в `.venv`, передайте `-Python C:\path\python.exe`. Обёртка передаёт параметры боту до импорта его DB-модуля и восстанавливает окружение PowerShell при завершении. Токены не выводятся. `-BotOnly` — явный запуск polling, а не проверка уже работающего экземпляра.

Обычная работа бота без `LIVE_TELEGRAM_TEST_ONLY=1` не меняется: диагностика и ограничение по тестовому ID выключены. Для тестового режима добавлен локальный lock-файл, предотвращающий запуск второго экземпляра с тем же probe. Это не замена проверке других серверов/компьютеров.

Только read-only preflight:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_live_telegram_test.ps1 -EnvFile .env.live -PreflightOnly
```

Без PowerShell:

```powershell
python scripts/live_telegram_smoke.py --env-file .env.live --interactive --timeout 120
```

## Прохождение

На каждом шаге сначала нажмите Enter в окне наблюдателя, **потом** выполните действие. Система проверяет свежие входящие updates, успешные ответы Bot API именно для этого update, завершение обработчика и снимки БД до/после. После автоматического подтверждения состояния она просит `yes / no / skip`: действительно ли ожидаемый ответ виден в клиенте? Никаких автоматических ответов за человека.

| Блок | Действия и автоматические свидетельства |
|---|---|
| Регистрация | `/start`, `/cancel`, повторный `/start`, некорректный никнейм, никнейм, роль, класс, языковая пара; проверяются реальные состояния `users.state` |
| Возврат | `/start` существующего профиля; очки и ответы не меняются |
| Задания | `/task`, кнопка пропуска, новое задание, начало исправления и `/cancel` |
| Подтверждение | После паузы нажать «Верно»; появляется ровно один новый ответ в БД с положительным `points_awarded` и соответствующим увеличением очков |
| Дубль | Повторная старая кнопка в другом клиенте, если она ещё доступна; проверяются конкретная уже отвеченная пара и неизменность очков/ответов. Если Telegram убрал кнопку, пропустите: недоступную кнопку тест не подделывает |
| Перезапуск FSM | Во время `awaiting_correction` остановить окно 1 через Ctrl+C, запустить ту же команду снова и отправить `/start`. Нужны новая сессия процесса, та же пара и сохранённое состояние |
| Исправление | Отправить иной обоснованный источником перевод; БД должна добавить ответ `action=correct`. Не выдумывать языковые данные ради зелёного теста |
| Профиль/рейтинг | `/me`, `/top` и периоды; доставка подтверждается Bot API, содержание проверяет человек, ответы и очки при просмотре не меняются |
| Доступ/справка | `/report`, `/privacy`, `/help`; у преподавателя требуется реальная доставка документа, у ученика — отказ, который подтверждает человек |

Для преподавателя нужен другой специальный аккаунт с ролью teacher: `-Role teacher` и соответствующий ID/env. Один аккаунт не доказывает обе роли. Если профиль уже полностью зарегистрирован, свежая регистрация помечается SKIP. Незавершённая регистрация продолжается с текущего этапа после /start; прежние шаги не засчитываются заново. Скрипт ничего не сбрасывает и не удаляет автоматически.

Можно запускать блоки `-Suite registration`, `-Suite tasks` и `-Suite profile`. Непроверенные блоки не становятся PASS. Если ручной шаг пропущен или истёк timeout, зависимая последовательность останавливается с `SKIP / MANUAL REQUIRED`; при незавершённом исправлении перед следующим запуском отправьте `/cancel`. Пропуск необязательного повторного callback или перезапуска допускает продолжение; они всё равно остаются SKIP.

## Удаление профиля

По умолчанию сценарий выключен. Только для специального тестового профиля:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_live_telegram_test.ps1 -EnvFile .env.live -Suite profile -AllowDelete
```

Понадобятся отдельная строка `DELETE TEST PROFILE` в консоли и `/delete_me` → «Да, удалить» в Telegram. Сам observer ничего не удаляет. Он проверяет, что Telegram ID больше не находит профиль, а прежняя запись действительно анонимизирована (`deleted_at`, пустой никнейм, нулевые очки). Рабочие аккаунты и результаты этим сценарием не тестируйте.

## Отчёт, приватность и завершение

`.live-telegram/report.json` обновляется после каждого результата. При повторном запуске прежний отчёт сохраняется рядом как `report-previous-*.json`, чтобы продолжение не уничтожило уже полученные свидетельства. Пока запуск не завершён, `report.summary.json` явно содержит `complete=false`, `status=SKIP`; частичный список строк PASS не является полным итогом. Там только название сценария, PASS/FAIL/SKIP и безопасное объяснение; `.progress.json` показывает текущий шаг. `probe.json` содержит heartbeat, PID/случайную сессию процесса, ID выделенного аккаунта и метаданные updates/успешных API-ответов. Тексты сообщений, переводы, class/teacher-коды, callback payload целиком и токены не записываются. Каталог и env исключены из Git; не публикуйте их.

Коды выхода: `0` — все записанные обязательные проверки подтверждены; `1` — обнаружена ошибка; `2` — есть SKIP/ручные непроверенные действия. Успешный `getMe` без пользовательской цепочки **всегда оставляет live E2E непроверенным**. В обычном запуске с одной ролью и выключенным удалением весь заявленный широкий набор останется частичным, даже если выполненные шаги PASS. Чужая роль, недоступная старая кнопка и неподтверждённое удаление не засчитываются автоматически.

При завершении/ошибке остановите observer Ctrl+C, затем polling Ctrl+C в окне 1. Observer не останавливает чужие процессы. БД/тома не удаляются. После нормального выхода polling его heartbeat помечается stopped и lock освобождается. Если процесс аварийно завершён, **сначала** убедитесь, что PID из probe больше не существует и других экземпляров нет; лишь затем удалите оставшийся локальный `.lock`. Тестовые данные сохраняются для разбирательства.

## Типичные ошибки

- `TelegramUnauthorizedError`: токен неверен/отозван; проверьте приватный env, не публикуя значение.
- Webhook активен: система его не меняет. Выберите правильный тестовый бот или отдельно решите вопрос отключения; очередь не сбрасывается.
- `TelegramConflictError` в polling: есть второй потребитель; остановите дубликат, не запускайте ещё один `getUpdates`.
- Probe отсутствует/устарел/не совпадает: проверьте единый env, путь, ID аккаунта, URL БД и работающий процесс с диагностикой.
- Нет состояния БД: проверьте REST/серверный ключ, импорт корпуса и код тестового класса. Не считайте сетевую ошибку отказом прав.
- Timeout: выполните действие **после** начала ожидания, используйте правильный Telegram-аккаунт и подтвердите ответ; неполные данные останутся SKIP.
- Бот отвечает другим пользователям: тестовый режим должен быть явно включён; не используйте этот тест как production polling.

## Автоматические проверки

`python -m unittest tests.test_live_telegram_smoke -v` проверяет изоляцию настроек, отказ устаревшей/чужой диагностики, корреляцию одной входящей команды с её успешным API-ответом, отсутствие секретных payload в журнале, запрет обработки сторонних аккаунтов в test-only режиме, неизменность очков при дубле и границы FSM/restart. Эти unit-тесты используют doubles и **не являются live Telegram E2E**. Существующий `tests/bot_integration.py` также сохранён.

Live-скрипт не добавлен в GitHub Actions и автоматически с настоящим токеном там не запускается. В CI продолжают работать unit и изолированный интеграционный контур. Основание протокола: [Telegram Bot API](https://core.telegram.org/bots/api#getwebhookinfo), [aiogram session middleware](https://docs.aiogram.dev/en/latest/api/session/middleware.html).
