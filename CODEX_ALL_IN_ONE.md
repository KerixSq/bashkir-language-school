## 1. Миссия продукта

Название: **«Башкирская языковая школа»**. Для учеников — **мультяшная приключенческая игра в мире Урала и башкирского эпоса**. Для сообщества — **система коллективной проверки и накопления переводов башкирского языка**. Для преподавателей — классы, отчёты, прогресс; для заказчика — воспроизводимая база и REST API.

Целевая аудитория: школьники, студенты, носители языка, преподаватели. Главный пользователь — ученик, который должен получать удовольствие от коротких занятий и ощущать пользу, а не заниматься заполнением базы ради статистики.

**Киллер-фича: «Библиотека Акбузата».** Игроки изучают язык и через независимые проверки переводов восстанавливают главы общей библиотеки. Общий прогресс привязан к реальным **уникальным подтверждённым переводам PostgreSQL**, а не к локальному XP, кликам или псевдоданным.

### Главный сценарий, который должен работать в действительности

`Источник БГПУ → импорт фрагментов → Telegram-задание → ответы ≥3 разных пользователей → SQL-консенсус → читаемый перевод → translations_export / REST API → сайт → увеличение прогресса Библиотеки Акбузата`.

### Сценарий ученика в веб-игре

`Приветствие и персонаж → карта мира → короткий урок (5 заданий) → обратная связь → XP и повторение ошибок → достижения/новая глава → возврат на следующий день`.

Не смешивать эти сценарии: **веб-упражнения для самостоятельного обучения** могут хранить персональный прогресс в браузере; **голоса, подтверждённые переводы, школьные рейтинги и коллективная библиотека** должны жить в защищённой серверной БД. Не обещать единую учётную запись/синхронизацию, если это не реализовано и не проверено.

- PostgreSQL и REST — Docker-контейнеры локального Supabase на ноутбуке.

## 6. Работа с корпусом БГПУ — критический правовой момент

Источник: https://huggingface.co/datasets/bashkorttele/trilingual-parallel-phrasebooks-bgpu

Ожидаемые локальные файлы:

```
data-ba-ru-alt.jsonl
data-ba-ru-ar.jsonl
data-ba-ru-kk.jsonl
data-ba-ru-sah.jsonl
data-ba-ru-zh.jsonl
```

Ожидаемые поля: `id`, `text_ba`, `text_ru`, `text_other`, `lang_other`, иногда `transcription`.

Импортируем **только** `ba-ru` (из всех файлов) и `ba-kk` (из kk). Повторы учитывать по нормализованному башкирскому тексту, но **не уничтожать смысловые различия знаков вопроса/восклицания** при дедупликации. Для русского варианта с разными исходными переводами сохранять статистику конфликтов и выбирать детерминированно; не выдавать частотный выбор за лингвистическую верификацию. Сохранять оригинальный ID, файл, позицию, источник. Повторный импорт не должен дублировать данные.

Подставной вариант — перевод другой фразы *из того же файла* со сходной длиной; он не должен совпадать с правильным. Это только технический эвристический вариант, не гарантия педагогической правдоподобности. Предусмотреть экспорт CSV для ручной проверки. Не импортировать синтетические переводы как настоящие.

**Лицензия:** ранее в проекте указывалась **CC BY 4.0**, но актуальная индексированная карточка Hugging Face может указывать **CDLA-Permissive-2.0**. Codex должен открыть страницу датасета и, главное, **фактические локальные `LICENSE` и `NOTICE`**, установить применимые условия и исправить проектную атрибуцию на основании источника. Не выбирать лицензию по привычке и не «исправлять» её догадкой. При отсутствии файлов/сети пометить вопрос как **BLOCKER к публичной публикации корпуса**. Лицензия текста не распространяется автоматически на иллюстрации, вёрстку изданий и музыкальное оформление.

Сам датасет предупреждает, что соответствие трёх языковых колонок не проверено построчно. Запустить ручную/экспертную проверку выборки, отличать `community_confirmed` от экспертно утверждённого.

- Яркие сине-зелёно-золотистые оттенки и светлый фон, выразительная типографика, дружелюбные крупные кнопки, аккуратные визуальные эффекты.
- Не вводить неподтверждённые «факты» о персонажах эпоса.
- Использовать уже созданные оригинальные материалы из `web/assets/`; проверить загрузку и оптимизировать размеры без потери качества.
- Мобильный интерфейс в приоритете: 360, 390, 430 px; затем планшет/десктоп.
- Контраст WCAG AA, клавиатура, фокус, `prefers-reduced-motion`, понятные ошибки/пустые состояния.

### P1.2 Уроки и личный прогресс

- По пять коротких заданий в уроке.
- Типы: выбор перевода, обнаружение ошибки, сбор из слов, ввод текста.
- Данные — из локальной колоды настоящих фраз БГПУ; если колоды нет, **честное пустое состояние**, а не придуманные фразы.
- Ответ: корректная проверка, пояснение, следующий шаг; повторение ошибок.
- Личные XP, ежедневная цель, серии, уровни, бейджи, открытия этапов — настоящие, с сохранением в localStorage **только если это локальный учебный прогресс**.
- Избегать манипулятивного удержания: не штрафовать детей агрессивными сериями, не показывать несуществующие достижения.
- Сайт не должен утверждать, что локальные учебные XP влияют на серверный консенсус.

### P1.3 Библиотека Акбузата — главная киллер-фича

- Общий прогресс: количество уникальных подтверждённых переводов из `translations_export`/`adventure_progress`, **за исключением источников license='demo'**.
- Учитывать активную языковую пару `ba-ru`/`ba-kk`, избегать двойного подсчёта.
- Для этапов использовать простые пороги из текущей реализации; проверить согласованность текста и реальных SQL-порогов (ранее встречались `1, 5, 15`; не выдумывать новый набор без причины).
- Краткое описание главы, реальный locked/unlocked, анимация при достижении порога, не при каждом открытии страницы.
- Состояния: загрузка, пусто, сеть недоступна, повторить запрос, подтверждение.
- Публичный API должен возвращать только агрегаты, не персональные записи детей.
- Для демо заранее подготовить реальную запись так, чтобы один новый подтверждённый перевод открыл следующую главу.

### P1.4 Telegram как игровая часть

- `/start`, `/task`, `/cancel`, `/me`, `/top`, `/report`, `/help`; дополнительные команды только если реально реализованы в репозитории (`/pair`, `/newclass`, `/privacy`, `/delete_me`).
- Короткие дружелюбные русские тексты через `bot/texts.py`.
- «Верно», «Исправить», «Пропустить», «Следующее задание» — работающие обработчики, защита от двойных кликов.
- После найденной подставной ошибки — короткая похвала; после подтверждения подставной ошибки — показ правильного перевода без начисления.
- Регистрация с проверяемым никнеймом, реальной языковой парой, школьным/учительским кодом.
- Уровень/очки/серия — только фактические SQL-значения.
- Логи с ротацией без токенов и идентификаторов детей, восстановление после сетевой ошибки.

## 10. Команды проверок (PowerShell, запускать из корня проекта)

```powershell
python -m compileall bot scripts tests
python -m unittest discover -s tests -v
python scripts/check_contract.py
python -m ruff check .
python -m ruff format --check .
```

Если Ruff не установлен, попроси разрешение установить **как dev-инструмент** (`python -m pip install ruff`) и зафиксируй версию в dev-настройках; если сеть недоступна, честно укажи «не запускался».

После запуска локального Supabase:

```powershell
npx supabase status
python scripts/check_rls.py
# Фактические параметры посмотри через --help или README:
python scripts/smoke_test.py --help
python scripts/demo_readiness.py --help
```

Для веба:

```powershell
python -m http.server 8000 --bind 127.0.0.1
```

Проверь вручную `http://127.0.0.1:8000/web/` в Chromium на нескольких размерах экрана. Обязательны реальные клики по игровым заданиям, профилю, рейтингу, API и сообщениям об ошибке. **Проверка JavaScript на синтаксис не означает, что сайт функционально работает.**

Для бота:

```powershell
python -m bot.main
```

В репозитории могут существовать дополнительные флаги CLI; **сначала читать `--help`/фактический код, не выдумывать параметры**.

### Как писать отчёт о проверках

| Категория | Допустимый результат |
|---|---|
| Unit tests | Конкретная команда, количество, PASS/FAIL |
| Python | `compileall` PASS/FAIL |
| SQL | `smoke_test.py` с реальной локальной БД: PASS/FAIL/NOT RUN |
| Права | `check_rls.py` с публичным ключом: PASS/FAIL/NOT RUN |
| Веб | Браузерное взаимодействие с указанием страниц/размеров: PASS/FAIL/NOT RUN |
| Бот | Реальный Telegram long polling: PASS/FAIL/NOT RUN |
| Ruff | Версия, check, format; либо NOT RUN + причина |

**Никогда** не подменяй «NOT RUN» на PASS только потому, что код выглядит корректным.

## 11. Приёмка продукта (Definition of Done)

Сборка готова к защите **только если**:

1. Локальный PostgreSQL сохраняет данные после перезапуска.
2. REST API отвечает через локальный Supabase и у него корректные права.
3. Миграции проходят при чистой установке и при обновлении на копии существующей базы.
4. Telegram-бот регистрирует человека и выдаёт реальное задание.
5. Ответ принимается, повтор не начисляется, подставной вариант обрабатывается правильно.
6. Три независимых пользователя подтверждают один перевод, и итог читаем.
7. `translations_export` и REST отдают этот перевод.
8. Библиотека Акбузата **увеличивает прогресс после подтверждения**, а не после кликов.
9. Веб-игра проходит полный урок из пяти заданий, XP сохраняется локально.
10. Локальные XP не меняют серверные рейтинги и коллективный консенсус.
11. Преподавательский отчёт защищён учительским кодом, ученик его не читает.
12. Экспертная очередь действительно принимает решение по спору.
13. Публичные представления не отдают персональные данные школьников.
14. Данные корпуса и лицензия корректно атрибутированы по фактическому LICENSE/NOTICE.
15. Все основные кнопки выполняют обещанное действие, есть ошибки/пустые состояния.
16. Мобильная версия удобна и доступна.
17. Тесты и Ruff выполнены или их объективные блокеры перечислены.
18. README позволяет повторить запуск на Windows 11.
19. Демо за три минуты воспроизводимо и не зависит от случайного выбора фразы.
20. Команда может честно объяснить, что реализовано, а что нет.

Если хотя бы один критичный пункт не подтверждён — результат «готова к интеграционной проверке», не «100% готова».

## 12. Порядок выполнения без лишних вопросов

**Фаза 1 — аудит:** прочитай репозиторий, покажи 5–10 крупнейших реальных рисков, подтверди стартовые команды. Дальше работай сам, не останавливайся после отчёта.

**Фаза 2 — P0:** локальная БД, миграции, Telegram, API, консенсус, безопасность, настоящие smoke/rls.

**Фаза 3 — P1:** веб-игра, мобильный UX, исправление учебных заданий, Библиотека Акбузата, стыковка с API.

**Фаза 4 — P2:** визуальная полировка, контент, документация, сценарий питча.

**Фаза 5 — независимый аудит:** перечитай изменения, проверь типичные регрессии, повтори всю проверку, сравни результаты с критериями приёмки.

После каждой фазы:

- перечисли изменённые файлы;
- укажи почему изменил;
- покажи реально запущенные команды и их результаты;
- сохрани безопасную Git-контрольную точку, если Git настроен;
- перечисли непроверенное;
- продолжай к следующей фазе, когда среда позволяет.

**Не задавай пользователю уточняющие вопросы, если можно сделать безопасное разумное допущение. Исключения:** удаление пользовательских данных, публикация секретов, выставление локального API в интернет, необратимые изменения или реальные недостающие ключи/доступы — там необходимо подтверждение или конкретное действие пользователя.

Представь результат по шаблону:
